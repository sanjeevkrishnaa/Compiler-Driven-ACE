# Full-scale TraceGen hotspot report

## Scope

This report analyzes three new TraceGen workloads on the same nominal scale as
the original compiler QFT trace: a 4×4 mesh with 16 cores, 96 logical qubits,
and eight qubit slots per core. TraceGen reserves two ancilla slots, so each
core initially holds six data qubits. The traces use HQA with OEE initial
placement, a `[0.1, 1.0]` reliability range, and seed 42.

The original `qft_requests.txt` is included as the reference workload. It was
not regenerated by TraceGen.

| Workload | Trace | Logical qubits | Compiler layers | Adjacent-hop requests |
| --- | --- | ---: | ---: | ---: |
| Original QFT | `C:\Users\sanje\Downloads\qft_requests.txt` | 96 | 766 | 4,954 |
| Cuccaro adder | `traces\cuccaro_96q_4x4_seed42.txt` | 96 | 1,458 | 132 |
| Draper adder | `traces\draper_96q_4x4_seed42.txt` | 96 | 1,710 | 1,908 |
| Random circuit | `traces\random_96q_d6000_4x4_seed42.txt` | 96 | 477 | 10,485 |

For each compiler layer, each hop consumes one communication endpoint at its
source core and one at its destination core. The principal capacity is three:
ACE gives compiler-directed preparation at most three of the four memories per
core, retaining one for application handoff or on-demand work. A layer is
marked overloaded when a core has more than three hop endpoints in that layer.

## Capacity sensitivity

| Workload | Active layers | Layers over 3 | Overloaded core-layers | Excess endpoint demand over 3 | Hops touching an overloaded core | Layers over 4 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Original QFT | 227 | 158 | 1,010 | 4,497 | 4,307 | 150 |
| Cuccaro | 33 | 1 | 10 | 46 | 44 | 1 |
| Draper | 295 | 87 | 181 | 272 | 635 | 27 |
| Random | 476 | 453 | 2,345 | 6,913 | 8,895 | 406 |

The workloads span three very different regimes:

- **Cuccaro** has sparse communication with one intense burst. Its layer 0
  contains 44 hop requests and peaks at 12 endpoints on core 10. The remaining
  32 active layers never exceed two endpoints per core.
- **Draper** has moderate but repeated contention. Eighty-seven of 295 active
  layers exceed three endpoints. Core 10 is the main hotspot with 419 incident
  hops, a peak of 10, and overload in 59 layers.
- **Random** is intentionally dense. It exceeds three endpoints in 453 of 476
  active layers. Its main hotspots are core 5 (2,656 incident hops, peak 16),
  core 6 (2,366, peak 19), core 4 (2,101, peak 14), and core 9 (1,964, peak 14).
- **Original QFT** is also highly congested: core 9 peaks at 28 endpoints in
  layer 372, followed by core 5 at 20 and core 8 at 16.

Giving compiler preparation all four memories helps only partially. It leaves
150 original-QFT layers, 1 Cuccaro layer, 27 Draper layers, and 406 random
layers above capacity. The random workload needs temporal scheduling or a
larger memory bank; changing the compiler reservation split alone cannot serve
its bursts.

## What this means for compiler pre-generation

The low compiler-pair coverage observed in the original QFT is consistent with
its capacity profile. Many future requests compete for the same three
compiler-eligible memories long before their application layer arrives. The
planner can reject some requests offline, and physical reservations can reject
more at runtime.

For Cuccaro, targeted pre-generation should be viable except around layer 0.
It is a useful workload for testing burst admission and communication
sublayers. Draper is better for testing bounded lookahead and request retry,
because hotspot pressure appears repeatedly but not in every layer. The dense
random trace is a stress test for admission control: its traffic routinely
exceeds even four simultaneous communication memories, so full coverage is not
feasible without splitting work across time.

## Reproduction commands

Run these from `C:\Users\sanje\Desktop\BTP\tracegen`:

```powershell
python generate.py --benchmark cuccaro --initial-placement oee --cores 16 `
  --reliability-min 0.1 --reliability-max 1.0 --width 96 --seed 42 `
  --output ..\repo\SeQUeNCe\example\multicore_entanglement\traces\cuccaro_96q_4x4_seed42.txt

python generate.py --benchmark draper --initial-placement oee --cores 16 `
  --reliability-min 0.1 --reliability-max 1.0 --width 96 --seed 42 `
  --output ..\repo\SeQUeNCe\example\multicore_entanglement\traces\draper_96q_4x4_seed42.txt

python generate.py --benchmark random --initial-placement oee --cores 16 `
  --reliability-min 0.1 --reliability-max 1.0 --width 96 --depth 6000 `
  --two-qubit-prob 0.7 --seed 42 `
  --output ..\repo\SeQUeNCe\example\multicore_entanglement\traces\random_96q_d6000_4x4_seed42.txt
```

The reusable validator and analyzer is
`tools/trace_analysis/analyze_trace_hotspots.py`. It checks the
initial placement, evolving qubit locations, and adjacency of every hop before
producing a JSON summary.
